# HTML 页面原型生成器

生成可用的视觉原型，而不是静态线框图。除非用户明确要求其他结构，否则只交付一个自包含的 HTML 文件。

## 适用边界

| 诉求 | 用什么 |
| --- | --- |
| 要一个能点、能发给别人看的独立方案稿 | 本 skill |
| 要落到 `apps/mobile` 的真实 Taro/React 组件 | `shape` 定方向 → `impeccable` 构建 |
| 已有界面的评审与收尾打磨 | `critique` / `polish` |

原型是**评审载体，不是实现来源**。不要把生成的 HTML 直接搬进 `apps/`。

## 输出约定

- 将结果写入用户指定的路径。用户未指定路径时，产品界面稿放 `UI-Preview/`，架构或流程可视化放 `docs/`；使用简短、描述性强、以 `.html` 结尾的 kebab-case 文件名，例如 `inventory-dashboard.html`。
- 将 HTML、CSS 和 JavaScript 放在同一个文件中。不得要求构建步骤、安装依赖、启动服务器或框架运行时。
- 确保文件以 `file://` 直接打开时可用。避免远程字体、脚本、样式表、API 和图片；离线页面确实需要视觉素材时，将用户提供或生成的图片嵌入为 data URI。
- 未经允许不得覆盖已有的用户文件；必要时使用不冲突的文件名。
- 在最终回复中说明生成的文件路径和已验证的交互。

## 将需求转为原型

1. 提取目标用户、核心目标、关键信息、所需操作、视觉特征、目标设备和明确约束。
2. 当需求基于已有产品改造时，先读 `docs/design-system.md` 与 `UI-Preview/` 下的既有稿，再检查相关截图或组件代码。复用真实的文案、术语和视觉惯例，不要设计脱离产品的界面。
3. 当需求不完整时，作出小范围且易于回退的假设。只有缺失信息会实质改变用户流程或页面类型时，才提出一个聚焦的问题。
4. 编码前在内部梳理用户的核心任务路径，并为这条路径赋予最高的视觉优先级，确保用户能在原型中完成它。
5. 为该路径建模必要的 UI 状态：选中的标签页、筛选值、打开的弹窗、表单草稿值、校验错误、空状态、完成反馈和本地模拟数据。

## 设计界面

- 让布局符合业务领域。运营工具应紧凑、易扫读且专注工作；当需求支持时，内容、消费和娱乐页面可以更具表现力。
- 将用户需要的实际体验作为首屏。不得用营销落地页替代应用或工具。
- 使用语义化区域和原生控件：`header`、`nav`、`main`、`section`、`button`、`label`、`input`、`select`、`dialog`，以及适用的表格或列表。
- 使用 CSS 自定义属性建立小型设计令牌集，涵盖颜色、间距、排版、边框、层次和动效。采用克制且有明确对比的多色系配色；不要依赖渐变背景、装饰性悬浮光团或过度圆角的卡片。
- **令牌命名对齐主题包**：改造已有产品时，内联令牌直接复用 `@litter-bear/theme` 的 `--lb-*` 名称与色值（语义与映射见 `packages/theme/src/css-variables.ts` 和 `docs/design-system.md`），配色限定在四套闭集主题内并在文件头注明用的是哪套。全新方向探索可自造命名，但要在文件头写明「未对齐 `--lb-*`，落地需重新映射」。原型与主题包各写一套色值，评审通过后落地时必然返工。
- 卡片只用于重复项目、弹窗或确实需要边框的工具。不要嵌套卡片，也不要将每个页面区块都做成悬浮面板。
- 当真实视觉媒体有助于理解目标产品、地点、人物或物件时，应纳入页面。优先使用用户提供的素材或嵌入式 data URI；没有可用素材时用纯 CSS 占位块并标注其代表的内容，不要用泛化装饰替代有意义的媒体。
- 文字按钮只用于明确命令。紧凑的工具操作用图标：单文件离线约束下**只有两种做法**——在文档顶部内联一组 `<svg><symbol>` 后用 `<use>` 引用，或直接用 emoji / Unicode 符号；二者选一并全页统一，不要逐个手绘散落的 SVG，也不要引 CDN 图标库。每个纯图标控件都必须具备无障碍名称和悬停/聚焦提示。
- 让展示文字与其容器相匹配。不要使用随视口缩放的字号或负字间距。约束布局，使长标签能有意地换行或截断，而不改变控件尺寸。
- 使用 grid、flex、最小/最大约束、媒体查询和适合触摸的点击区域，明确实现所有响应式行为。检查窄屏移动端和桌面端。
- 不要只为填满页面而添加可见的产品内说明、快捷键列表或功能介绍。

## 面向 apps/mobile 的原型约束

当原型的落地目标是 `apps/mobile`（Taro 4 → 微信小程序）时，只用小程序渲染层能实现的能力，否则原型越精致、落地时推翻得越彻底：

- 布局用 flex / grid、百分比与固定尺寸；尺寸用 rem（`weapp-tailwindcss` 按 rem → rpx 换算），不用 `vw` / `vh` 字号或 `clamp()`。
- 不用 `<dialog>`、`:has()`、`backdrop-filter`、`position: sticky` 嵌套滚动容器、CSS `@container`、复杂伪元素动画链。弹窗用普通 `div` + 遮罩层模拟。
- 阴影、圆角、渐变限定为主题包已有的 `--lb-shadow-*` / `--lb-radius-*` / 线性渐变；不用 `oklch()`。
- 长列表、下拉刷新、滚动吸顶等交互标注清楚即可，不必在 HTML 里做高保真实现。

原型目标是 Web/桌面或纯方案探讨时，本节不适用，按常规 Web 能力自由发挥。

## 实现有意义的交互

- 使用原生 JavaScript 和 DOM。将状态保存在一个小而命名清晰的对象中，并以确定性的方式渲染状态变更。
- 实现需求隐含的每项交互，例如切换标签页、打开和关闭模态框或抽屉、搜索和筛选列表、切换视图模式、选择项目、增删本地记录、展开详情、提交表单、校验字段、切换设置和展示短暂反馈。
- 确保交互控件可通过键盘操作。保留清晰的焦点样式；通过原生元素支持用 `Escape` 关闭可关闭的浮层，用 `Enter` 或 `Space` 触发按钮操作。
- 后端数据不可用时，使用明确的本地模拟数据集。不得声称模拟操作已经更新远程系统。
- 避免无效控件。删除草稿中没有设计行为的按钮、菜单项、开关或导航元素。
- 使用 `aria-live` 展示成功和校验反馈。为对话框提供标签；对话框打开时锁定焦点，防止背景发生不适当的滚动，并在关闭后将焦点还给触发控件。
- 遵循 `prefers-reduced-motion`。保持过渡短且有目的，绝不让交互依赖动效结束。

## 交付前验证

先判断当前会话有没有浏览器能力（Playwright / Puppeteer / 浏览器 MCP）。两条路径的产出不同，**不得混淆**。

**有浏览器工具时：**

1. 检查保存的文件存在，并且在需要交互时包含有效的文档结构、内联样式和内联脚本。
2. 通过可用浏览器或渲染器直接打开 HTML。对于独立文件，不要启动开发服务器。
3. 操作每个声明的交互，包括主操作、存在时的浮层或展开状态、存在时的表单校验，以及重置或关闭路径。
4. 在桌面视口（约 1440px 宽）和移动端视口（约 390px 宽）下检查截图。修复空白区、裁切、重叠、水平溢出、难以阅读的对比度，以及落在视口外的控件。
5. 确认页面在相关情况下，面对模拟数据、空结果和较长标签时仍清晰易懂。

**没有浏览器工具时**（本仓库当前默认情况）——降级为静态自查，逐项核对：

1. 文件存在，文档结构完整，样式与脚本均已内联，无外链资源。
2. 通读脚本：每个绑定的事件都有对应实现，状态对象的每个字段都被渲染消费，没有引用不存在的 DOM id。
3. 响应式断点在源码中确实存在；容器有 `max-width` 或 `min-width` 约束，无已知的水平溢出写法（固定宽度 > 390px、`white-space: nowrap` 的长文本）。
4. 触摸目标 ≥ 44px；焦点样式未被 `outline: none` 清除；对话框有标签与 `Escape` 关闭路径。
5. 前景/背景对比度按色值估算达到 WCAG AA。

降级路径下，最终回复必须写明「**未做浏览器渲染与截图验证，请本地打开确认**」，并列出上述已完成的静态检查项。禁止把静态自查表述为「已在 1440px / 390px 下验证」——这违反根 `AGENTS.md` 的诚实链路约定。

## 交付清单

- 交付一个可直接在浏览器打开的 `.html` 文件。
- 确保文件中包含所有被请求的视觉内容和行为。
- 不留下 TODO 文本、虚假的点击目标、控制台错误或依赖安装步骤。
- 只汇报文件路径、关键交互以及会影响草稿的简要假设。
- 说明令牌是否已对齐 `--lb-*`；未对齐时明确写出落地需重新映射。
- 如实说明验证方式：浏览器截图验证 vs 静态自查，不夸大。
