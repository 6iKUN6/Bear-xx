# 一期自媒体 Bot 渲染能力整合方案

日期：2026-10-31
状态：方案设计稿。基于仓库现有代码事实与开发规范梳理，供渲染工具化（阶段 2）及后续 Bot / vibe 制片复用。本方案只描述「怎么组织代码」，不等同于已完成实现。

---

## 一、目标与范围

一期要交付一个自媒体 Bot，产出一条 vibe 知识大赏视频。渲染能力从「独立 render 节点」演进为「agent 可自主调用的 `renderHtmlToVideo` 工具」，并让同一套渲染执行逻辑可被节点、工具、后续 vibe 制片流程复用。

本文回答三个问题：

1. **复用什么**——哪些现有模块直接拿来用，不改边界。
2. **抽取什么**——哪些逻辑当前重复或耦合，应抽成独立模块。
3. **怎么组织**——模块划分、依赖方向与可维护性做法。

---

## 二、规则要求（硬约束）

以下规则来自根 `AGENTS.md`、`apps/api/AGENTS.md` 及现有代码约定，本方案及后续实现必须遵守。

### R1 能力注册闭集
工具一律经 `CapabilityRegistry` 闭集注册（含 schema、权限、风险、失败语义），由 `CapabilityResolver` 按决策装配。禁止在业务层散落具体工具实例。

### R2 契约单一源
渲染参数边界（宽高偶数、时长、帧率、HTML 体积上限）唯一来源是 `packages/types/src/agent-flow/definition.ts` 的 `FLOW_RENDER_LIMITS` 与 `FlowRenderNode` 契约。工具、节点、管理端、Zod schema 都从它引用，禁止各处各写一份上下限。

### R3 幂等语义统一
成片对象的上传复用 `CosStorageService` 的「不可变声明 + 内容摘要」幂等机制。禁止另造一套「先删再写」或「到期重发」的覆盖逻辑。同一请求复用同一成片，同一 key 绝不接管重写。

### R4 长任务边界
渲染是长任务（30 分钟级），不得混入普通节点的 5 分钟 Activity。含渲染能力的执行路径必须独立配置超时与心跳，且普通 agent 执行超时不得截断渲染。

### R5 不新增过度抽象
只为「消除真实重复」或「明确降低复杂度」才抽层。禁止为工具化引入 wrapper / adapter / bridge / mapper 这类无第二实现的抽象层。单实现逻辑优先内聚。

### R6 编排唯一路径
所有任务执行走 AgentFlow；工具装配由 Flow 节点声明的 `toolGroups` / `skills` 驱动，不由模型自由猜策略。

### R7 注释与提交规范
新增方法按 `apps/api/AGENTS.md` 要求写中文注释（入参/出参/作用）；提交信息中文、subject 小写开头（commitlint 约束）。

## 三、现有模块盘点（直接复用，不改边界）

| 模块 | 路径 | 职责 | 复用方式 |
|---|---|---|---|
| 渲染内核 | `modules/html-render/html-render.service.ts` | HTML → 本地 mp4（逐帧截图 + FFmpeg），含取消、进度回调、临时目录释放 | **原样复用**，不改造 |
| COS 幂等上传 | `modules/storage/cos-storage.service.ts` | 对象存在性校验 + 不可变声明 + 内容摘要上传 | **原样复用**，`objectExists` / `putObjectIfAbsent` |
| 对象 key 生成 | `modules/html-render/render-object-key.ts` | 由稳定身份生成成片 key | **原样复用** |
| 工具装配 | `modules/ai/agent-loop/capability/capability.registry.ts` + `capability.resolver.ts` | 工具/工具组/审批/元数据登记与装配 | **原样复用**，新工具走 `registerTool` |
| 工具组定义 | `modules/ai/agent-loop/capability/tool-groups.ts` | 工具组常量闭集 | 新增 `render` 组，不改机制 |
| 任务上下文 | `modules/ai/telemetry/model-call-context.ts` | ALS 任务上下文（taskId / userId / isTest） | **原样复用**，已扩展 isTest 读取 |
| 契约常量 | `packages/types/src/agent-flow/definition.ts` | `FLOW_RENDER_LIMITS`、`FlowRenderNode` | **原样复用**，引用不复制 |
| 渲染 worker 角色 | `modules/html-render/render-worker-role.ts` | 渲染只允许在 Activity Worker 执行 | 复用，归属长任务边界 |

**结论**：渲染的「内核」（HtmlRenderService）和「落库/上传」（CosStorageService）已经分层清晰，**不需要动**。工具化要解决的不是内核，而是「谁在什么身份下调用内核」这一层。

## 四、模块抽取策略（新增独立模块）

### 4.1 核心抽取：渲染执行编排

**问题**：当前「读 HTML → 构造执行身份 → 幂等存在性检查 → 渲染 → 幂等上传 → 返回 path」这段流程存在**两份重复实现**：

- `agent-flow/temporal/agent-flow.activities.ts` 的 `executeRenderNode`
- `ai/tools/renderHtmlToVideo.ts`（工具）

两者除「HTML 来源」和「执行身份」不同外，渲染 + 上传的编排逻辑完全一致。继续各自维护必然漂移（幂等语义、取消释放、错误归类各改各的）。

**方案**：抽取一个 `RenderPipelineService`（渲染编排服务），承担「一段 HTML + 渲染参数 + 执行身份 → 成片 path」的完整编排，节点与工具都复用它。

```ts
interface RenderPipelineInput {
  html: string;
  width: number;
  height: number;
  durationSeconds: number;
  fps: number;
  /** 幂等身份：稳定标识，重试复用同一成片 */
  execution: CosObjectExecution;
  /** 内容摘要，参与 COS 幂等校验 */
  inputDigest: string;
  /** 取消信号与帧进度回调，由调用方注入 */
  signal?: AbortSignal;
  onFrame?: (progress: { frame: number; totalFrames: number }) => void | Promise<void>;
}
```

职责边界：**只做编排**（存在性检查 → 渲染 → 上传 → 释放），不做 HTML 来源解析，不做身份决策。身份由调用方（节点 / 工具）传入，保证两者可复用同一份逻辑。

### 4.2 不建议抽取的（明确拒绝）

- **不抽「渲染工具层」**：工具只是 `RenderPipelineService` 的薄封装，不需要再套 adapter。
- **不抽「工具调用身份解析器」**：身份构造差异只在两处各几行，抽成共享服务反而增加跳转。
- **不抽「长任务调度抽象」**：长任务归属 Temporal 层（见 §5），不引入通用调度框架。

### 5.2 依赖方向（单向，禁止反向）

```txt
packages/types (契约)
   ↑ 只被引用
ai/tools (工具)  ──►  RenderPipeline (编排)  ──►  html-render (内核)
                                                  └─► storage (上传)
agent-flow/temporal (节点执行)  ──►  RenderPipeline (编排，同上)
capability (装配)  ──►  ai/tools (工具工厂)
model-call-context (ALS)  ──►  提供 taskId / userId / isTest 给工具
```

关键约束：

1. **工具与节点不互相依赖**，都只依赖 `RenderPipeline`，从根上消除重复。
2. **`RenderPipeline` 不依赖 Temporal**。取消信号与心跳通过回调注入（`signal` / `onFrame`），由调用方（Activity 或工具）负责接入自己的心跳/取消机制。
3. **`ai` 模块不反向依赖 `agent-flow`**。工具只依赖渲染内核、上传、编排、ALS，与 Flow 解耦。
4. **契约只被引用**。任何模块不复制 `FLOW_RENDER_LIMITS` 的值。

### 5.3 长任务边界的归属

长任务改造（阶段 2 步骤 4）拆成三层，各自归属清晰：

| 层 | 归属 | 做法 |
|---|---|---|
| 快照标记 | `temporal/workflows/*.types.ts` + 快照构建处 | `AgentFlowWorkflowNode` 加 `longRunning` 标记，编译时识别含 `render` 工具组的 agent 节点 |
| 超时分发 | `temporal/workflows/agent-flow.workflow.ts` | 长超时 `executeNode` 代理 + 按标记分发，workflow revision 升级 patch 保护旧 History |
| 心跳/取消 | `RenderPipeline` 的 `onFrame` / `signal` 回调 | 渲染期间由调用方注入心跳，工具执行时由 agent Activity 层转发 |

## 六、可维护性具体做法

### M1 渲染执行逻辑单一源
`RenderPipeline` 是「HTML → 成片 path」的唯一实现，节点与工具只传身份、不复制编排。后续 vibe 制片流程直接复用，新增渲染来源只需新增调用方。

### M2 幂等身份显式化
执行身份（`CosObjectExecution`）由调用方显式传入，工具用内容寻址（`hash(html+参数)`）、节点用执行标识，都在调用边界确定，不在编排层隐式猜测。

### M3 取消与心跳经回调注入
`RenderPipeline` 通过 `signal` / `onFrame` 接收外部机制，不 import Temporal 或 `ActivityContext`。这样编排逻辑可在单测里用假回调验证，不依赖真实 Temporal。

### M4 错误分类收敛到内核
渲染失败原因码（`HtmlRenderErrorCode`）由 `html-render` 定义，`RenderPipeline` 只负责归类「可重试 / 不可重试」，调用方据此决定重试策略。禁止在各调用方重复写错误判断。

### M5 测试策略
- `RenderPipeline`：构造坏例（缺帧接口、HTML 超限、上传失败、取消）验证编排与释放。
- 工具：验证幂等复用（同参数返回同 path）、内容寻址 key 稳定性。
- 长任务：真实 Temporal 集成验证超时不截断（沿用 `agent-flow.workflow.spec` 的时序敏感约定，偶发单例先重跑）。

### M6 版本与回退
工具化作为独立可 review 增量提交；`RenderPipeline` 抽取与工具/节点改造分步提交，每步 build + lint + 相关单测通过。旧 render 入口在工具路径验证通过后按存量清单有序退出，不边拆边删。

## 七、落地顺序（结合阶段 2 剩余步骤）

| 顺序 | 事项 | 产出 |
|---|---|---|
| 1 | 抽 `RenderPipeline`，`executeRenderNode` 与工具改为调用它 | 消除重复，行为不变 |
| 2 | skill 注册（渲染指令注入 systemPrompt） | agent 知道何时/如何调渲染 |
| 3 | 长任务边界（快照标记 + 超时分发 + 心跳注入） | 工具渲染不被 5 分钟截断 |
| 4 | 旧工件盘点 + 工具版发布 + 旧入口退出 | 有序迁移 |
| 5 | 整体验收（阶段 3） | 新任务端到端出片 |

> 说明：当前已完成「工具注册」一步（`renderHtmlToVideo` 工具 + `render` 工具组 + ALS 扩展 isTest）。第 1 步「抽取 RenderPipeline」是消除当前两份重复实现的直接动作，建议紧接实施。

---

## 八、一句话总结

**内核不动、编排抽一、身份显式、长任务单列**：复用现成的渲染内核与 COS 幂等上传，把「HTML → 成片 path」的编排抽成唯一的 `RenderPipeline`，节点与工具各传自己的执行身份，长任务走独立的 30 分钟 Activity——这样渲染能力只维护一份实现，vibe 制片、Bot 作品管理都能直接复用。
